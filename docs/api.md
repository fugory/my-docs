# API 参考

以下接口仅用于文档展示，不提供真实服务。目的是演示怎样把请求、参数、返回值和错误情况写清楚。

## 查询文档列表

- 请求方法：`GET`
- 请求路径：`/api/docs`
- 功能：返回文档条目列表。

### 请求参数

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `page` | integer | 否 | 页码，从 1 开始，默认 1 |
| `size` | integer | 否 | 每页条数，默认 20，最大 100 |
| `q` | string | 否 | 按标题模糊搜索 |

### 返回示例

```json
{
  "items": [
    {"id": 1, "title": "使用指南"}
  ]
}
```

### 完整返回结构

```json
{
  "items": [
    {"id": 1, "title": "使用指南", "updated": "2026-11-17"}
  ],
  "total": 1,
  "page": 1,
  "size": 20
}
```

## 获取单篇文档

- 请求方法：`GET`
- 请求路径：`/api/docs/{id}`

```bash
curl -s https://example.com/api/docs/1
```

## 错误码约定

| 状态码 | 含义 | 触发场景 |
| --- | --- | --- |
| `200` | 成功 | 正常返回 |
| `400` | 参数错误 | `size` 超过 100，或 `page` 小于 1 |
| `404` | 资源不存在 | `id` 对应的文档被删除 |
| `429` | 请求过于频繁 | 超过每分钟 60 次 |

错误响应统一带上可读信息，方便前端直接展示：

```json
{
  "error": "invalid_parameter",
  "message": "size 最大为 100"
}
```

## 一点实践体会

写这份 API 文档时发现，**最容易漏的是错误码**。

正常路径谁都写得出来，但真正影响使用体验的是"参数写错了会怎样"。把错误码列成表、给出错误响应样例，使用者才能在拿到 400 时知道自己改哪里，而不是去翻源码。

文档的价值，很大程度上体现在这些**不顺利的分支**上。
