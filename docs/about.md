# 关于本项目

## 项目目标

实现从 Markdown 文档到公开网站的自动化发布：源文件只写一次，之后每次推送由 CI 自动构建并发布，不依赖本地环境，也不用手工上传。

## 技术组成

| 工具 | 作用 |
| --- | --- |
| Markdown | 编写文档内容 |
| MkDocs Material | 将文档构建成静态网站 |
| GitHub Actions | 自动执行安装、构建和部署 |
| GitHub Pages | 托管并提供网站访问地址 |

## 四个部分怎么串起来

```
docs/*.md  ──mkdocs build──▶  site/  ──artifact──▶  Pages  ──▶  公开网址
  源文件                     构建产物              发布               访问
```

理解这张图的关键是分清两样东西：

- **`docs/` 是源**，人写，提交进仓库，是唯一的真相来源。
- **`site/` 是产物**，机器生成，每次构建都可以从 `docs/` 完整重建，所以不提交、加进 `.gitignore`。

产物不提交有个额外好处：仓库里永远不会有"某次手工改过 site/ 但没改对应源文件"的不一致状态。

## 为什么选 MkDocs Material

有几个静态站点生成器都能干这件事。选它的理由是：

1. **零前端代码**。不需要写路由、组件、构建配置，一个 `mkdocs.yml` 就够。
2. **`--strict` 有用**。它把内部链接失效、配置拼写错误升级成构建失败，配合 CI 等于免费的文档体检。
3. **中文支持开箱即用**。`language: zh` 一行就切好界面语言和搜索分词。

## 一点实践体会

以前觉得"文档站"是个很轻的东西，真做一遍才发现它的价值不在渲染，而在**约束**：

- 内容必须以 Markdown 存在，因此可以 diff、可以 review、可以回溯。
- 发布必须经过构建，因此坏链接进不去。
- 部署必须是自动的，因此文档和代码不会各走各的。

这三条约束合起来，才是"文档不会腐烂"的原因。
